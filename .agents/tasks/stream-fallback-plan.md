# Implementation Plan — Streaming graceful fallback + Example shim real streaming

Goal: when the streaming attempt fails because streaming is unsupported, `OpenAIProvider.chatStream` falls back to a single non-streaming request and delivers the full answer (instead of surfacing the hard error the user saw). Separately, give the Example app's `openai` shim a real streaming path so it can stream against LM Studio.

## Design decisions (grounded in the code I read)

- **Detection stays in the library, not the shim.** `OpenAIProvider.chatStream` is the one place both `chat()` and `chatStream()` funnel through, so a fallback here fixes every caller regardless of which client backs it. The shim's thrown message `"Streaming is not supported in the React Native shim."` matches the required case-insensitive substring `"streaming is not supported"`, so the library fallback triggers correctly even before the shim gains a streaming path. This gives two independent layers of defense.
- **Narrow fallback match.** Only the four streaming-unsupported phrases trigger the fallback. Connection/network errors must keep flowing to the existing `isConnectionError()`/`isLocalHost()`/`buildConnectionHelp()` path — so the fallback check runs on the inner streaming error and, if it does NOT match, the error is rethrown to the existing outer `catch`. This preserves the actionable local-LLM help message.
- **Structure: inner try around streaming only.** Wrap just the `create({stream:true})` + `for await` iteration in an inner `try`. On a streaming-unsupported error, run the non-streaming request inline (still inside the outer `try`), so any genuine failure of the fallback request (e.g. connection refused) still reaches the outer connection-error handling unchanged.
- **Usage parity.** Fallback reuses the existing `estimateTokens` import, `serializeContext()`, and the exact same `AIUsage` shape and `estimated` semantics already in this file — no duplicated helpers.
- **Shim streaming is defensive about Hermes.** RN fetch under Hermes may not expose `response.body.getReader()`. Try the incremental reader + `TextDecoder` path; if unavailable, fall back to `await response.text()` and parse the whole SSE buffer. Guard `TextDecoder` existence. The async iterable yields OpenAI-shaped chunks so the library's `for await` loop reads `chunk.choices[0]?.delta?.content` and `chunk.usage` with no library change needed.

## Notes / assumptions

- `chat()` keeps returning `Promise<string>` and `OpenAIProvider` stays exported from `src/index.ts` — neither needs editing; the fallback is entirely inside `chatStream`.
- `LocalAIProvider` is left as-is (still throws not-configured) per the requirement.
- The fallback's SINGLE `onToken(fullText)` call means a non-streaming server renders the whole answer at once — acceptable and expected per requirement 1 ("deliver that whole text ... as a SINGLE onToken call").
- No runtime LM Studio call is part of verification (no server guaranteed in the build environment); verification is build/type-check/syntax only, which is the project's real gate.
