# AppLens React Native Library — Initial Implementation

AppLens is a four-FEAT implementation of an in-app developer console for React Native. The library ships raw TypeScript consumed directly by Metro, provides a floating trigger + full-screen six-tab modal, intercepts XHR and fetch globally, captures console output, and connects to OpenAI via the `openai` npm package. All four FEATs are marked completed and both `tsc --noEmit` commands exit 0.

Watch for: (1) **confirmed** — `index-project.js` companion script is missing; only `CodeIndexer.ts` was created. (2) **confirmed** — `SettingsTab` toggles call `AppLens.initialize()` on every flip, but interceptors are not re-attached/detached when `network` or `console` is toggled off at runtime. (3) **confirmed** — `initialize()` in Triveni Point is called inside `useEffect`, meaning network and console interception doesn't start until after the first render cycle — any synchronous logs or network calls during module-level initialization are missed. (4) **likely** — `AppLensTrigger`'s `position:'absolute'` inside `<SafeAreaProvider>` + `<RootNavigator>` stacking may not float correctly on all Android devices.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The storage, interceptor, and type layers are solid. `MemoryStorage` correctly enforces ring-buffer eviction and notifies subscribers synchronously. `NetworkInterceptor` redacts all six required headers (`authorization`, `cookie`, `x-api-key`, `x-auth-token`, `x-access-token`, `x-secret`) with case-insensitive matching across both the XHR and fetch paths. TypeScript strict mode passes in both repos.

All six tabs render and the `AITab` shows a setup prompt rather than crashing when no API key is configured. The `AppLensProvider` context stays live via storage subscriptions.

The Triveni Point integration is additive — no existing code removed — but placing `initialize()` inside `useEffect` instead of at module level creates a blind spot: any network calls or console output from module-level imports (Redux store hydration, `axios-provider`, Firebase init) run before interceptors are attached and are never captured.

The `SettingsTab` exposes toggles for `network` and `console` that call `AppLens.initialize()` on every flip. Because `initialize()` skips interceptor management after the first call, toggling these flags changes `config` but leaves the underlying interceptors in their original state. There is no runtime path to stop or restart interceptors after startup.

The `index-project.js` companion CLI entrypoint is referenced in both the plan and README but was never created. Running `node src/ai/index-project.js /path/to/app` as documented will fail with `Cannot find module`.

<details>
<summary>Issues (4)</summary>

1. **Missing `index-project.js`** — The companion CLI entrypoint (`src/ai/index-project.js`) referenced in the plan and README was never created. The README's `node src/ai/index-project.js /path/to/app` command will throw `Cannot find module`. Create a minimal JS wrapper: `const { indexProject } = require('./CodeIndexer'); indexProject(process.argv[2]).then(m => console.log(JSON.stringify(m, null, 2)));`.

2. **Settings toggles don't affect running interceptors** — `SettingsTab` calls `AppLens.initialize(updated)` on every toggle, but `initialize()` skips interceptor management on second+ calls. Toggling `network: false` leaves `NetworkInterceptor` attached and still storing requests; toggling `console: false` leaves `ConsoleInterceptor` running. Either expose `detach()` on the singleton and call it when flags flip to false, or document that feature toggles require an app restart to take effect.

3. **`useEffect` initialization creates an early-boot blind spot** — `AppLens.initialize()` in `App.tsx` fires after the component tree is committed. Module-level side effects (`axios-provider` import, Redux store hydration, Firebase init) run before this, so any network calls or console output in that window are never captured. Move `initialize()` to module level outside the component: `if (__DEV__) { AppLens.initialize({...}); }`.

4. **Floating trigger z-index on Android** — `AppLensTrigger` uses `position:'absolute', zIndex:9999` inside `<SafeAreaProvider>`. On Android, z-index is per-elevation and does not cross View hierarchies, so any navigation-level modal or elevated surface from `RootNavigator` may render above the trigger. The standard fix is to render the trigger as a direct child of the root `View` in `App`, outside `SafeAreaProvider`.

</details>

<summary>Details</summary>

### Settings toggle gap and interceptor lifecycle (confirmed)

`AppLens.initialize()` sets `this.initialized = true` on the first call and skips all interceptor logic on subsequent calls. `SettingsTab` calls `initialize(updated)` on every `Switch` toggle to propagate config changes. The result: toggling `network: false` leaves `NetworkInterceptor` attached and silently continues capturing requests. Toggling `console: false` has the same non-effect for console capture. The UI provides false confidence that the feature is disabled.

To fix, either: (a) add `updateConfig(partial)` to the singleton that mutates config without the initialized guard and calls `detach()` / `attach()` as needed, or (b) make the toggle labels read "Requires restart" and accept the limitation.

### Early-boot blind spot (confirmed)

`App.tsx` wraps `AppLens.initialize()` in `useEffect(() => {}, [])`, which runs after the first render commit. In Triveni Point, the module-level `import './src/services/axios-provider'` side effect runs synchronously at bundle evaluation time. Any console output or network calls from `axios-provider`, the Redux store slice initializers, or Firebase app init happen before `useEffect` fires and are never captured. Moving initialization outside the component fixes this:

```ts
if (__DEV__) {
  AppLensDebug.initialize({
    enabled: true,
    network: true,
    console: true,
    events: true,
    ai: true,
    projectRoot: '/Users/sunilkumar/Desktop/project/AppLens/triveni-point',
  });
}
```

### Missing `index-project.js` (confirmed)

`CodeIndexer.ts` exports `indexProject()` and is present, but the plan (step 17) and README both direct users to run `node src/ai/index-project.js /path/to/app`. That file does not exist. `CodeIndexer.ts` cannot be run directly with `node` because it uses TypeScript syntax. A plain JS wrapper of ~3 lines is the minimum viable fix.

### Test coverage gap

No tests exist for AppLens. The XHR prototype override, ring-buffer eviction at the exact capacity boundary, and `ContextEngine` keyword matching are all behavioral correctness concerns that `tsc --noEmit` cannot catch. This is an acknowledged iteration constraint per the task context, not a regression, but it means any future refactor of the interceptor or storage layer has no safety net.
